## Q1. Mid-stream SSE recovery on Claude 4.6+ (Skill 2.1)

A streaming support agent running `claude-opus-5-5` with the Python SDK (`max_retries=2`) receives HTTP `200`, streams two complete sentences in a `text` block, begins emitting a `tool_use` block with partial JSON arguments, and then receives `event: error` (`overloaded_error`).<Cite id="F1 F5" /> A recovery handler catches the exception and retries by placing the partial `text` and incomplete `tool_use` blocks into a final assistant message as a prefill. Every recovery attempt immediately fails with HTTP `400` (`invalid_request_error`).<Cite id="F3 F4" /> **Server-sent events (SSE)** carry events after the stream response starts.

**Which recovery change should the engineering team implement?**

- **A.** Increase the SDK client's `max_retries` to `5` and let the built-in HTTP backoff handler resume the interrupted stream automatically.
- **B.** Drop the incomplete tool call, keep completed text, and continue in a new `user` message.
- **C.** Keep the partial `text` block in an assistant prefill message, close the truncated `tool_use` JSON locally, and resubmit the request to the same endpoint.
- **D.** Forward the identical prefilled assistant history to an Amazon Bedrock regional endpoint so the extra capacity avoids `overloaded_error`.

<SelfCheck question="Answer to Q1">

**B.** Mid-stream SSE errors arrive after HTTP `200`, so SDK HTTP retry does not resume the stream.<Cite id="F1 F5" /> Discard the incomplete `tool_use` block and continue from completed text in a new `user` message. Claude 4.6+ rejects assistant prefill, and tool or thinking blocks cannot be partially recovered.<Cite id="F2 F3 F4" /> A **circuit breaker** pauses calls after a bounded failure window; use one for repeated transient failures, then serve cached or reduced-function responses for noncritical work. Keep safety refusals on their own handling path. (Engineering recommendation.)

</SelfCheck>

## Q2. Cross-platform failover and feature parity (Skill 2.1)

A production analysis pipeline on the first-party Claude API relies on `code_execution` and `fallbacks="default"` (`server-side-fallback-2026-07-01`). During a regional capacity event causing sustained `529` and `429` errors, an engineer first switches `inference_geo` from `"us"` to `"global"` on the first-party API, which leaves rate-limit headroom unchanged. Next, the engineer redirects failover traffic to an Azure-hosted Microsoft Foundry deployment, where requests immediately fail with `400 Bad Request`.<Cite id="F6 F7 F10" />

**Which failover architecture provides an independent capacity pool while preserving `code_execution` and beta feature parity?**

- **A.** Fail over to **Claude Platform on AWS**, using its separate capacity pool and support for `code_execution` and beta features.
- **B.** Keep traffic on the first-party Claude API and alternate requests between `inference_geo: "us"` and `inference_geo: "global"` to double available rate-limit capacity.
- **C.** Route failover traffic to an Amazon Bedrock regional CRIS endpoint without altering the request payload, because Bedrock regional endpoints carry a 10% premium for full server-tool parity.
- **D.** Keep `code_execution` enabled on the Azure-hosted Microsoft Foundry deployment and add the SDK's `BetaRefusalFallbackMiddleware` to bypass the `400 Bad Request` responses.

<SelfCheck question="Answer to Q2">

**A.** **Claude Platform on AWS** runs on a separate capacity pool from both the first-party Claude API and Amazon Bedrock, while providing the full Anthropic platform experience including the Messages API, `code_execution`, and beta features.<Cite id="F8 F9" /> Option B fails because `inference_geo` values (`"us"` and `"global"`) share the same rate-limit pool.<Cite id="F6" /> Option C fails because Amazon Bedrock regional CRIS pricing reflects data-residency routing rather than server-side fallback or server-tool parity.<Cite id="F10 F12" /> Option D fails because Azure-hosted Microsoft Foundry rejects `code_execution` with `400 Bad Request` by design, and client-side refusal-fallback middleware only retries safety refusals rather than `400` parity errors.<Cite id="F7 F11" />

</SelfCheck>

## Q3. Distinguishing spend-cap `429`s, refusals, and retry storms (Skill 2.1)

An orchestrator wraps the Python `anthropic` client (default `max_retries=2`) in an outer 3-attempt loop that retries every `429`, `529`, and `stop_reason == "refusal"`.<Cite id="F5" /> During an incident, telemetry shows three patterns: (1) several `429` responses carry `error.details.error_code: "enforced_spend_limit_reached"` with no `retry-after` header; (2) several HTTP `200` responses return `stop_reason: "refusal"` with `stop_details.category: "reasoning_extraction"`; and (3) `529` brownouts cause upstream request volume to spike dramatically.<Cite id="F13 F16" />

**Which TWO changes address the evidenced failure modes? Select TWO.**

- **A.** Fail fast on `enforced_spend_limit_reached` and route `reasoning_extraction` refusals to prompt review instead of retrying them.
- **B.** Disable stacked retries (`max_retries=0` on the SDK client or remove the outer loop) and enforce a per-client retry ratio budget with jittered backoff for transient `429`/`529` responses.
- **C.** Configure `BetaRefusalFallbackMiddleware` with a fallback model list so `"reasoning_extraction"` refusals automatically retry on a secondary Claude model.
- **D.** Increase the SDK `timeout` above 10 minutes and set `inference_geo: "global"` so `"enforced_spend_limit_reached"` requests draw from an unused tier budget.
- **E.** Re-send `"reasoning_extraction"` refusals to the same model with a higher `max_tokens` value so the classifier clears on the next attempt.

<SelfCheck question="Answer to Q3">

**A, B.** A tier spend-cap `429` (`enforced_spend_limit_reached`) has no `retry-after` header and keeps failing until access resumes, so stop retrying and alert billing or operations.<Cite id="F13" /> A `reasoning_extraction` refusal has no recommended fallback model; route it to prompt review rather than retrying it.<Cite id="F16" /> Disable one of the stacked retry loops and set a per-client retry budget; jittered backoff can limit added load during transient errors.<Cite id="F5 F14" /> **Backpressure** slows or rejects incoming work when downstream capacity is constrained. A bounded queue with admission control can apply it; when queue wait would exceed the interactive SLA, return a defined degraded response or reject the work. (Engineering recommendation.) Option C fails because the refusal category has no recommended fallback model.<Cite id="F16" /> Option D fails because `inference_geo` shares the same rate-limit pool and cannot bypass a tier spend cap.<Cite id="F6 F13" /> Option E fails because resending a refusal to the same model usually results in another refusal.<Cite id="F15" />

Read response outcomes separately: an HTTP `200` with `stop_reason: "model_context_window_exceeded"` is a valid but truncated response. Reduce or compact context; do not classify it as a transient rate-limit error.<Cite id="F74" />

</SelfCheck>

## Q4. Cache-aware **ITPM** (input tokens per minute) vs. **OTPM** (output tokens per minute) (Skill 2.2)

A production service on `claude-sonnet-5-5` (Start tier: 4,000 RPM, 2,000,000 ITPM, 400,000 OTPM) runs steadily at 500 requests/minute.<Cite id="F19" /> Each request sends a 10,000-token system prompt (cached), 1,500 uncached user tokens, `max_tokens: 4096`, and averages 350 generated output tokens. Immediately after a deploy inserts a per-request timestamp at the top of the system prompt, requests begin failing with HTTP `429` and `anthropic-ratelimit-input-tokens-remaining: 0`, while `anthropic-ratelimit-output-tokens-remaining` stays above `200000`.

**What caused the `429` errors, and which change restores throughput headroom?**

- **A.** Remove the variable timestamp so requests reuse the cached prefix and reduce ITPM charges.
- **B.** Lower `max_tokens` from `4096` to `512` on every request so Claude reserves fewer tokens against the organization's OTPM rate limit.
- **C.** Keep the timestamp in the system prompt and pace requests smoothly at ~8 requests/second so token-bucket bursts stop triggering `429` responses.
- **D.** Distribute the 500 requests/minute across `claude-sonnet-4-6` and `claude-sonnet-4-5` in separate workspaces so each model and workspace receives an independent 2,000,000 ITPM budget.

<SelfCheck question="Answer to Q4">

**A.** Only `input_tokens + cache_creation_input_tokens` count toward default ITPM, whereas `cache_read_input_tokens` are excluded.<Cite id="F17" /> The timestamp changed the cached prefix, so each request missed the cache and paid for uncached input or a new cache write. That charged all 11,500 input tokens per request (`500 × 11,500 = 5,750,000` ITPM), exceeding the 2,000,000 Start-tier limit for `claude-sonnet-5-5`.<Cite id="F17 F19 F75" /> Option B fails because OTPM counts actual generated output tokens rather than `max_tokens`, and OTPM still has over 200,000 tokens remaining.<Cite id="F18" /> Option C fails because smoothing bursts cannot resolve a sustained 5.75M ITPM deficit against a 2M ceiling.<Cite id="F17 F19" /> Option D fails because Sonnet 4.6 and Sonnet 4.5 share one combined Sonnet 4.x rate-limit bucket and organization-wide limits still apply across workspaces.<Cite id="F20 F21" />

</SelfCheck>

## Q5. Ramp limits vs. batch windows and spend limits (Skill 2.2)

After 12 hours of near-zero weekend traffic, an interactive Monday-morning dashboard surge immediately dispatches 2,500 requests/minute to `claude-sonnet-5-5` on a Scale-tier organization (well below its steady-state RPM, ITPM, and OTPM limits). Requests immediately fail with HTTP `429`, `error.type: "rate_limit_error"`, `error.details.error_code: "ramp_limit_exceeded"`, and `retry-after: 12`, while `anthropic-ratelimit-tokens-remaining` headers still show millions of tokens available. Users require synchronous sub-10-second responses.

**Which change best prevents these Monday-morning `429` failures?**

- **A.** Raise the workspace spend limit in the Claude Console and disable `retry-after` sleeps so failed requests retry immediately.
- **B.** Move the interactive dashboard requests to `POST /v1/messages/batches`, because the Message Batches API is exempt from ramp limits.
- **C.** Ramp traffic gradually from recent peaks, pace through admission control, and honor `retry-after`.
- **D.** Split the 2,500 requests/minute evenly across five workspaces whose custom rate limits sum to the organization's Scale-tier ceiling.

<SelfCheck question="Answer to Q5">

**C.** A `ramp_limit_exceeded` `429` occurs when token usage grows faster than the model's recent per-minute peak plus a step, even when steady-state ITPM/OTPM headroom remains.<Cite id="F22 F23 F24" /> As an engineering practice, pacing traffic up gradually in steps while honoring `retry-after` lets successful usage lift the ramp ceiling without triggering `429` rejections.<Cite id="F23 F27" /> Option A fails because user-configured spend limits return HTTP `400 invalid_request_error` rather than `ramp_limit_exceeded`, and ignoring `retry-after` violates rate-limit guidance.<Cite id="F24 F25 F27" /> Option B fails because Message Batches are asynchronous with up to a 24-hour processing window and do not satisfy a synchronous sub-10-second SLA.<Cite id="F26" /> Option D fails because ramp limits cap the organization's growth on the model and organization-wide limits still apply across workspaces.<Cite id="F21 F22" />

</SelfCheck>

## Q8. Remote MCP auth migration and ZDR boundaries (Skill 2.3)

A compliance-bound fintech team plans to migrate an internal ledger MCP server from `https://mcp-old.internal/mcp` to `https://mcp.example.com/mcp` and connect it directly via the Messages API MCP connector while keeping their organization's Zero Data Retention (ZDR) guarantee for all ledger tool calls and outputs. During staging tests on the new URL, clients presenting tokens minted for the old URL receive HTTP `401`, and a developer suggests passing the client's MCP bearer token straight through to the downstream ledger API.

**Which assessment and action should the architect take?**

- **A.** Refresh resource metadata and audience-bound tokens, use separate downstream credentials, and keep ZDR-covered calls off the connector.
- **B.** Pass the client's MCP bearer token through to the downstream ledger API to eliminate extra credential exchanges, and rely on the organization's Messages API ZDR flag to cover MCP connector tool results.

- **D.** Remove the retrieval pipeline and pass the entire 5-million-token engineering corpus directly in every Messages API prompt.

<SelfCheck question="Answer to Q10">

Option B asks the model to answer without evidence and removes permission to admit uncertainty.<Cite id="F63" /> Option C cannot recover evidence absent from initial candidates and leaves the ACL flaw. </SelfCheck>
