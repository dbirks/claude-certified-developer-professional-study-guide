## Q1. Subagent permission inheritance and callback bypass (Skill 1.1)

An internal release-engineering service built on the Claude Agent SDK runs the main session with `permission_mode="acceptEdits"` and dispatches a `schema-auditor` subagent configured with `AgentDefinition(description=..., prompt=..., permissionMode="default")`. Engineers placed a path check inside the parent `canUseTool` callback to block edits under `migrations/` while prompting via Slack for `Bash` commands. Production traces show `Bash` calls pause for Slack approval as expected, but `Edit` calls targeting `migrations/004_drop_col.sql` succeed without `canUseTool` ever running.

**Which change best enforces the `migrations/` restriction for the subagent?**

- **A.** Set `permissionMode="dontAsk"` on the `schema-auditor` `AgentDefinition` and add an explicit instruction in `prompt` never to modify `migrations/`.
- **B.** Add `disallowed_tools=["Agent(fork)"]` and `allowed_tools=["Edit"]` on the parent options so non-forked subagent edits route through `canUseTool`.
- **C.** Move the `migrations/` path check into a `PreToolUse` hook configured with `on_failure="block"` that returns `deny` for matching file paths.
- **D.** Inspect `Edit` arguments inside a `PostToolUse` hook and instruct the parent agent in `CLAUDE.md` to revert unauthorized changes to `migrations/`.

<SelfCheck question="Answer to Q1">

**C.** Tool permissions execute in a fixed six-step order where `PreToolUse` hooks run first and auto-approved tools skip `canUseTool` altogether, so moving the check to a fail-closed `PreToolUse` hook (`on_failure="block"`) returning `deny` blocks the edit deterministically before execution.<Cite id="F6 F9 F71 F72" /> Option A fails because a subagent under an `acceptEdits` main session inherits `acceptEdits` (overriding its own `permissionMode`), and prompt instructions are not deterministic controls.<Cite id="F7" /> Option B fails because `Agent(fork)` only disables forked subagents while adding `Edit` to `allowed_tools` still auto-approves edits before `canUseTool`, and Option D runs `PostToolUse` only after the edit has succeeded.<Cite id="F6 F73 F74" />

</SelfCheck>

## Q2. Handoff degradation and premature verifier passes (Skill 1.1)

A platform team orchestrates feature delivery across four sequential subagents (`planner`, `implementer`, `tester`, and `reviewer`), passing full Markdown plans, git diffs, and raw test logs back through the coordinator's conversation history. Cost traces show 68% of total tokens are spent re-summarizing context between handoffs, edge-case requirements from the initial spec vanish by the `tester` step, and the `reviewer` subagent repeatedly reports `PASS` after running only one or two smoke checks despite failing boundary cases.

**Which orchestration redesign best addresses both the token bloat and the premature passes?**

- **A.** Keep the four role-based subagents, enable `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` so teammates read a shared task list, and raise `maxTurns` on `reviewer`.
- **B.** Consolidate coupled stages by context boundary, store large outputs externally returning lightweight references, and require full-suite plus negative tests in the verifier prompt.
- **C.** Upgrade all four subagents to `opus` and instruct the coordinator to forward every prior subagent's full transcript verbatim into the next stage's prompt.
- **D.** Keep the four role-based subagents, enforce `output_format` JSON schemas on every handoff, and double `maxTurns` on `reviewer` so it runs deeper checks.

<SelfCheck question="Answer to Q2">

**B.** Decomposing along context boundaries rather than tightly coupled SDLC roles reduces handoff loss and coordination spend, storing large structured outputs externally with lightweight references eliminates coordinator copying overhead, and explicitly requiring full suites, edge cases, and negative tests counters the verifier "early victory" failure mode.<Cite id="F1 F2 F3" /> Option A adds peer mailbox and shared task-list coordination without fixing role-handoff bloat, while higher `maxTurns` in Options A and D does not prevent early-victory passes.<Cite id="F3 F11" /> Option C increases token burn further without preventing handoff loss, and Option D's JSON schemas still pass bloated role-handoff state through the coordinator instead of splitting by context boundary.<Cite id="F1 F2" />

</SelfCheck>

## Q3. Serverless HITL blocking and runaway subagent fan-out (Skill 1.1)

A webhook service runs an Agent SDK worker (wrapping `claude -p`) inside a 15-minute serverless function to investigate security alerts and draft fixes. Production telemetry surfaces two recurring failures: (1) workers block inside `canUseTool` for up to 45 minutes waiting on human Slack sign-off for destructive `Bash` commands, triggering function timeouts; and (2) complex alerts trigger recursive subagent spawning three levels deep up to 20 concurrent workers, causing HTTP 429 rate-limit cascades and spiking `ResultMessage.modelUsage` spend.

**Which TWO changes best eliminate both the serverless timeout and the runaway fan-out? Select TWO.**

- **A.** Increase the HTTP client `max_retries` setting to `10` so HTTP 429 responses from the 20 concurrent workers automatically recover without bounding concurrency.
- **B.** Return `permissionDecision: "defer"` from a `PreToolUse` hook on gated commands so the `-p` turn exits with `stop_reason: "tool_deferred"` and resumes after Slack approval.
- **C.** Replace `PreToolUse` hooks with `AskUserQuestion` inside each subagent so operators approve commands asynchronously without touching parent callbacks.
- **D.** Raise the serverless function timeout to the platform maximum and set `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` to coordinate approvals across peer workers.
- **E.** Cap recursion with `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1` alongside a bounded `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` and `max_budget_usd` ceiling.

<SelfCheck question="Answer to Q3">

**B, E.** Returning `permissionDecision: "defer"` from `PreToolUse` ends the `-p` turn cleanly with `stop_reason: "tool_deferred"` and preserves the pending call in the transcript for later resumption without holding a process open, while setting `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1`, a lower `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` cap, and `max_budget_usd` prevents deep recursion (default 3 layers, 20 workers) and halts overspending with `error_max_budget_usd`.<Cite id="F5 F10 F75 F83" /> Option A retries rate limits without reducing concurrency or recursion depth.<Cite id="F24 F75 F83" /> Option C still pauses execution via `canUseTool` (and `AskUserQuestion` is unavailable inside `Agent`-spawned subagents), and Option D leaves a blocking process waiting on approval while Agent Teams ignores teammate spawning in `-p` and Agent SDK runs.<Cite id="F8 F11 F76 F77" />

</SelfCheck>

## Q4. Crash mid-tool execution and state recovery boundaries (Skill 1.2)

An Agent SDK billing agent running on ephemeral containers writes an audit row to Postgres via `Bash`, then invokes a non-idempotent `issue_credit` tool (`idempotentHint: false`) that POSTs to an external payments gateway. Immediately after the gateway returns `200 OK` and issues the credit, the container is terminated by `SIGKILL` before the `tool_result` is appended to the `SessionStore` transcript. A replacement container starts and prepares to call `resume` on the stored `session_id`.

**What happens on `resume`, and which design prevents duplicate credits during crash recovery?**

- **A.** `resume` re-executes the dangling `issue_credit` call automatically; call `rewind_files()` before `resume` to revert both the external credit API call and the `Bash` Postgres row.
- **B.** `resume` skips the interrupted `issue_credit` call; back the tool with a durable step log and deterministic idempotency key to return cached results or reconcile in-flight state.
- **C.** `resume` skips the interrupted `issue_credit` call; parse the raw `~/.claude/projects/<encoded-cwd>/*.jsonl` file on startup and re-run any trailing `tool_use` block lacking a `tool_result`.
- **D.** `resume` re-executes the dangling `issue_credit` call only if `session_store_flush="eager"` is set; raise SDK `max_retries` to `5` so interrupted calls replay safely.

<SelfCheck question="Answer to Q4">

**B.** Resuming a session does not re-execute a tool call that was interrupted by a crash.<Cite id="F13" /> Because `issue_credit` is non-idempotent (`idempotentHint` false) and an external `200 OK` may commit before the transcript updates, the tool layer needs a durable write-ahead step log with a deterministic idempotency key to replay cached `SUCCEEDED` receipts or reconcile `IN_FLIGHT` uncertainty before calling the gateway again.<Cite id="F13 F25" /> Option A fails because `rewind_files()` restores only tracked tool-edited local files—leaving `Bash` side effects, external HTTP calls, and conversation history intact.<Cite id="F12 F15 F16" /> Option C relies on internal JSONL schemas that can break across releases and still risks double-charging, while Option D mistakes SDK HTTP retries and eager transcript flushing for external tool idempotency.<Cite id="F14 F24 F78" />

</SelfCheck>

## Q5. Mid-session model migration with preserved thinking (Skill 1.2)

Ahead of the November 30, 2026 retirement of `claude-sonnet-4-5-20250929`, a platform team migrates active multi-turn sessions to `claude-sonnet-5-5` and rolls out a new top-level `system` prompt regulatory disclosure between turns. Resumed sessions fail with HTTP `400 invalid_request_error`, first rejecting `thinking.type` on migrated sessions and—after switching `thinking` and deploying the `system` update—failing on subsequent `claude-sonnet-5-5` turns with `Invalid signature in thinking block. The block is bound to a different conversation.`

**Which remediation resolves both errors for active sessions without breaking preserved thinking on subsequent turns?**

- **A.** Continue routing active sessions to `claude-sonnet-4-5-20250929` with `max_retries=5` until they finish, because Anthropic keeps retired models available for active sessions.
- **B.** Keep `thinking: {"type": "enabled", "budget_tokens": 4096}` and strip every prior assistant thinking block from `messages` before forwarding requests to `claude-sonnet-5-5`.
- **C.** Deploy a custom proxy to re-sign prior thinking blocks under the `claude-sonnet-5-5` schema while continuing to edit the top-level `system` prompt per turn.
- **D.** Set `thinking: {"type": "adaptive"}`, keep active sessions on their last `system` and `tools` snapshot (or use `prefix_mismatch_behavior: "drop_block"`), and expect a cold cache.

<SelfCheck question="Answer to Q5">

**D.** Preserved-thinking models such as `claude-sonnet-5-5` reject `thinking: {"type": "enabled"}` with a `400` error and require `"adaptive"`, while keeping active conversations on the `system` and `tools` of their last successful request prevents prefix-check `400` failures (and `thinking.block_binding.prefix_mismatch_behavior: "drop_block"` with beta header `thinking-binding-controls-2026-08-01` recovers already-broken threads).<Cite id="F20 F21 F22" /> Switching models also starts with an uncached history read because prompt caches are model-scoped.<Cite id="F19" /> Option A ignores scheduled model retirement (after at least 60 days' notice), Option B still sends rejected `"enabled"` thinking, and Option C fails because thinking blocks remain tied to their exact prior `system`, `tools`, and message prefix.<Cite id="F18 F20 F79" />

## Q7. Evaluating workflow-to-agent trial metrics at scale (Skill 1.3)

A fintech team runs a randomized production A/B trial on 5,000 eligible compliance-exception cases per arm under identical tool permissions, evaluator rubrics, and a 60-second SLA. The deterministic workflow resolves 3,900 cases (78%) for $1,950 total ($0.50 per success, p95 = 22s) with 150 failed tool calls out of 10,000 (1.5%, affecting 2.9% of cases). The bounded single agent resolves 4,500 cases (90%) for $2,475 total ($0.55 per success, p95 = 48s) with 450 failed tool calls out of 30,000 (1.5%, affecting 8.2% of cases). Business criteria require at least 88% resolution, p95 at or under 55s, and value each incremental resolution at $1.50.

**How should the team interpret these results when deciding whether to evolve the system?**

- **A.** Reject the bounded agent because tripling absolute failed tool calls (450 versus 150) indicates the downstream tool API degraded under agent traffic.
- **B.** Reject the bounded agent because its $0.55 cost per successful case exceeds the workflow's $0.50 baseline and pushes total spend up by $525.
- **C.** Advance the bounded agent to canary (or route exception cohorts) after human validation, since incremental wins cost $0.875 within SLA, and track the 8.2% case exposure separately.
- **D.** Replace both arms with a multi-agent orchestrator-workers setup, since multi-agent systems consume about 4x chat tokens while improving resolution across dependent workflows.

<SelfCheck question="Answer to Q7">

**C.** Evaluating systems requires multidimensional criteria rather than a single cost metric, as agents often trade higher cost and latency for better task completion.<Cite id="F31 F45" /> Here the agent meets the 88% and 55s thresholds at $0.875 per incremental success ($525 divided by 600 extra resolutions, well under the $1.50 value), and the unchanged 1.5% per-call error rate shows the dependency did not degrade—3x more tool calls per case simply exposed 8.2% of cases to at least one failed call. Option A misreads call-level versus task-level failure rates, Option B ignores incremental business value and SLA targets, and Option D misstates Anthropic's ~15x-versus-chat multi-agent data (4x is for single agents) while ignoring that dependent workflows are poorly suited to multi-agent systems.<Cite id="F30 F34 F84" />

</SelfCheck>

## Q8. Evolving a predictable agent back to a deterministic workflow (Skill 1.3)

Six months after deploying an autonomous invoice-coding agent inside a third-party wrapper framework, trace audits show that 94% of production runs execute the exact same 3-step sequence (`fetch_vendor` then `classify_gl` then `validate_tax`) with negligible branching and a strict 4-second p95 latency target. However, the third-party wrapper obscures the underlying prompts and responses during debugging and prevents engineers from inserting deterministic human-approval and conditional-execution gates before calling `post_ledger`.

**Which architectural change best improves latency, debuggability, and execution control?**

- **A.** Migrate the stable 94% path to a deterministic workflow on a Messages API manual loop so application code controls the fixed sequence, inspects raw requests, and enforces gates before `post_ledger`.
- **B.** Retain the autonomous agent and switch to the Messages SDK `tool_runner` (`@beta_tool`), which gives finer per-call human approval and conditional execution control than a manual loop.

- **D.** Split the 3-step sequence across three Agent Teams teammates so each teammate checks the previous step's result through peer mailboxes before `post_ledger`.

<SelfCheck question="Answer to Q8">

**A.** When a task follows well-defined, predictable paths, workflows orchestrated through predefined code paths provide better consistency and simpler execution than an autonomous agent, and Anthropic recommends a manual Messages API loop whenever human-in-the-loop approval, custom logging, or conditional execution is needed while removing framework abstractions that obscure prompts.<Cite id="F29 F30 F32 F33 F35" /> Option B reverses the SDK guidance because `tool_runner` handles default loops and leaves manual loops for approval and conditional gates.<Cite id="F35" /> Option C provisions a cloud container per session without removing wrapper opacity or adding deterministic pre-ledger gates, and Option D adds peer-team coordination overhead to a deterministic 3-step path.<Cite id="F11 F37" />

</SelfCheck>

## Q10. Cache occupancy, Haiku 5.5 pricing cliff, and tool bloat (Skill 1.4)

## Q11. Cache-safe mid-conversation steering, compaction, and usage auditing (Skill 1.4)

**Which TWO changes resolve the cache misses, rule loss, `content: null` summaries, and billing under-reporting? Select TWO.**
