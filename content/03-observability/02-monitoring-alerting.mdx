<KeyPoints>

- Refusals, `max_tokens`, and `model_context_window_exceeded` ride HTTP `200` with `stop_reason`, so classify terminations, not status codes alone; Claude Code logs refusals as `claude_code.api_refusal`.<Cite id="F11 F12 F19" />
- For a 30-day SLO, consider paging on `1h/5m` at `14.4x` and `6h/30m` at `6x`, and ticketing on `3d/6h` at `1x`. Adjust for quiet endpoints.<Cite id="F4 F5 F6" />
- Page spend on OTel metrics or the legacy `/cost_report`; the Analytics API lags 4-to-24 hours and revises until about 7 days after month end.<Cite id="F14 F16 F18" />
- Cost growth with ITPM `429`s on flat traffic warrants checking `usage.cache_read_input_tokens`: cache reads are excluded from default cache-aware ITPM limits.<Cite id="F23 F34" />
- Spend failures differ: `429` with `enforced_spend_limit_reached` has no `retry-after`, while a limit you configured returns `400 invalid_request_error` (`429` in Claude Code workspaces).<Cite id="F30" />

</KeyPoints>

**Production monitoring** turns live responses into ratios and holds them against targets. A **service level indicator** (SLI) is a quantitative measure of some aspect of service level, aggregated as a rate, an average, or a percentile; a **service level objective** (SLO) sets the target value or range for it.<Cite id="F1" /> The **error budget** is the permitted fraction of unsuccessful events under an SLO. **Burn rate** measures how fast the service consumes that budget relative to the SLO window.<Cite id="F3" /> Monitor response outcomes as well as HTTP status: `stop_reason` reports why generation ended on a successful response.<Cite id="F11" />

## How it works: signals, budgets, and burn rate

Keep the SLO set small. Google SRE advises choosing just enough SLOs to cover the system's key attributes rather than over-constraining teams.<Cite id="F2" /> Anthropic recommends evaluating most use cases against multiple success criteria.<Cite id="F9" /> Choose criteria such as task success, latency, safety, and cost to suit the service.<Cite id="F9" />

The error budget is the SLO's complement: a `99.9%` target leaves `0.001`. Burn rate divides the observed error ratio by that budget: `1` spends the whole budget inside the compliance window, `14.4` 14.4 times faster.<Cite id="F3" /> One window cannot decide an alert, so Google SRE's **multi-window, multi-burn-rate** (MWMBR) pattern pairs a long window for precision with a short window that confirms burn is active; one-twelfth of the long window is a guideline, so the alert clears soon after recovery.<Cite id="F4" /> For a 30-day `99.9%` SLO the starting points are `14.4x` (`2%` of budget in `1h`, short window `5m`) and `6x` (`5%` in `6h`, short window `30m`) for paging, plus `1x` (`10%` in `3d`, short window `6h`) for tickets.<Cite id="F5" />

As engineering practice, cover four layers, not one availability number.

| Layer | What the SLI counts | Signal it reads |
|---|---|---|
| **Completion yield** | Valid responses that reached a usable terminal state | `stop_reason` on every HTTP `200` Messages response, plus the status code itself<Cite id="F11" /> |
| **Latency** | First-token time and full-turn time, tracked apart | TTFT for streaming and interactive apps;<Cite id="F7" /> `ttft_ms` on `claude_code.llm_request` and `interaction.duration_ms` on `claude_code.interaction` spans<Cite id="F20" /> |
| **Behavior and quality** | Refusals, tool failures, task success, grounded answers | `stop_reason: "refusal"` with `stop_details.category`;<Cite id="F12" /> `claude_code.tool_result`;<Cite id="F19" /> `pass^k`;<Cite id="F25" /> citation-verification pass rate<Cite id="F10" /> |
| **Unit economics** (cost per unit of work) | Spend per successful task and cache efficiency | Analytics cost rows;<Cite id="F15" /> cache-read share in Console rate-limit charts<Cite id="F23" /> |

Low traffic makes error ratios noisy: a single failure in a quiet window can push a computed burn rate past a paging threshold, so Google SRE recommends synthetic traffic, aggregating related services, retries or fallbacks, or wider windows for low-volume services and quiet periods.<Cite id="F6" /> Keep synthetic and real-user results visible separately: successful probes can mask user failures.<Cite id="F38" />

## Latency, stop reasons, and quality SLIs

**Time to first token** (TTFT) measures how long the model takes to generate its first output token after receiving the prompt, and helps measure responsiveness in streaming and interactive applications.<Cite id="F7" /> Anthropic separates **baseline latency** — prompt processing and response generation independent of token throughput — from TTFT, and exposes `output_config.effort` to trade latency against reasoning depth, with `"low"` on Claude Haiku 5.5 as the example.<Cite id="F8" /> Keep TTFT separate from full-turn percentiles: a turn can include several model calls and tool executions.

Termination quality sits in the response body. `stop_reason` is part of every successful Messages API response and says why generation ended — `end_turn`, `max_tokens`, `stop_sequence`, `tool_use`, `pause_turn`, `refusal`, or `model_context_window_exceeded` — whereas errors mean the request itself failed to process.<Cite id="F11" /> A classifier refusal on supported Claude Fable and Opus models, Sonnet 5.5, or Haiku 5.5 arrives as a normal response, not an error, with `stop_reason: "refusal"` and `stop_details.category` naming the policy area.<Cite id="F12" /> For streaming, read the final `stop_reason` from `message_delta`; it is null in `message_start`.<Cite id="F36" /> Claude Code's OpenTelemetry export encodes that split: refusals land on a successful stream, so `claude_code.api_error` does not fire and `claude_code.api_refusal` carries refusal frequency instead.<Cite id="F19" />

Groundedness and tool health need their own indicators. Make answers auditable by having Claude cite quotes and sources per claim, then verify each claim by finding a supporting quote after generation; the pass rate is your grounded-answer rate.<Cite id="F10" /> Compute tool failure rate from execution results — `claude_code.tool_result` carries `tool_name`, `success`, `duration_ms`, and `error_type`<Cite id="F19" /> — but excludes rejected tool calls; track decisions separately.<Cite id="F37" /> Managed Agents exposes per-tool counts and failure rates in the Console Inspector **Tools** tab.<Cite id="F22" /> For agent tasks, report `pass@k` (at least one success in `k` attempts) and `pass^k` (all `k` succeed), since `pass^k` measures consistency across those trials, which can help assess production reliability.<Cite id="F25" />

Targets below are illustrative 30-day baselines for a retrieval-and-tool workload, not Anthropic thresholds.

| SLI | Definition | Illustrative 30d SLO |
|---|---|---|
| Completion availability | `200` with `end_turn` or handled termination, over valid requests | `>= 99.9%` |
| Streaming TTFT | Dispatch to first output token (`ttft_ms`)<Cite id="F7 F20" /> | `p95 <= 1,200 ms` |
| End-to-end latency | Full turn, for example `interaction.duration_ms` in Claude Code<Cite id="F20" /> | `p95 <= 12 s` (RAG) |
| Task success | Sampled tasks passing an outcome or calibrated-judge check (`pass^1`)<Cite id="F25 F26" /> | `>= 96.0%` |
| Grounded-answer rate | Sampled answers whose claims are all cited and entailed<Cite id="F10" /> | `>= 98.0%` |
| Tool failure rate | Failed executions over completed executions; track rejected calls separately<Cite id="F19 F22 F37" /> | `<= 2.0%` |
| Safety refusal rate | Responses with `stop_reason: "refusal"` over all `200`s<Cite id="F12 F19" /> | Investigate changes against a baseline |
| Cache hit rate | `cache_read_input_tokens` over total input tokens<Cite id="F23" /> | `>= 80%` |
| Cost per successful task | Total cost over successful tasks<Cite id="F15" /> | `<= $0.045` |

## Token and cost telemetry

The **Usage and Cost Analytics API** is the reconciled source. `GET /v1/organizations/analytics/usage` and `GET /v1/organizations/analytics/cost` are in beta and require `anthropic-beta: analytics-usage-cost-2026-08-24` on every request, alongside `anthropic-version`.<Cite id="F13" /> Amounts are decimal strings in USD cents with six decimal places, so `"41280.000000"` is $412.80, and `cost_type` and `token_type` breakdowns sit outside the five-dimension `group_by[]` cap.<Cite id="F15" /> The data is not live: it typically refreshes within 4 hours, can take up to 24, and stays revisable until about 7 days after calendar month end.<Cite id="F14" /> For a consistent cutoff, use `data_refreshed_at` as an upper bound for `ending_at`; later reconciliation can still revise earlier values.<Cite id="F14" />

The **legacy Usage and Cost API** (`/v1/organizations/usage_report/messages` and `/v1/organizations/cost_report`) stays supported at roughly 5-minute freshness, making it the faster spend-anomaly check, while Anthropic still recommends the Analytics API for new integrations for its extra dimensions, request counts, and Default Workspace IDs.<Cite id="F16" />

Push telemetry covers the real-time lane. Claude Code exports OpenTelemetry metrics as time series — `claude_code.cost.usage`, `claude_code.token.usage`, `claude_code.session.count`, `claude_code.code_edit_tool.decision`, and `claude_code.active_time.total` — plus structured events and optional beta traces.<Cite id="F18" /> Claude Code tracing is off by default and needs `CLAUDE_CODE_ENABLE_TELEMETRY=1`, `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1`, and `OTEL_TRACES_EXPORTER`; `claude_code.llm_request` spans then record `ttft_ms`, `first_content_ms`, `duration_ms`, `error_class`, and `stop_reason`; `first_content_ms` and `error_class` require Claude Code v2.1.268 or later.<Cite id="F20" /> Claude API and SDK spans are in beta, follow the GenAI semantic conventions, and report the tokens your organization is billed for even when the request fails or the application cancels it.<Cite id="F21" /> Managed Agents sessions emit cumulative `session.usage` events holding `list_cost`, `active_seconds`, and budget state on idle transitions and budget pauses.<Cite id="F22" />

The Console **Usage** page charts *Rate Limit - Input Tokens*, which includes the cache-read percentage, and *Output Tokens*.<Cite id="F23" /> For coding-agent fleets, `GET /v1/organizations/usage_report/claude_code` returns daily per-actor productivity, tool acceptance and rejection counts, and estimated model costs at up to a 1-hour lag, with an Admin API key.<Cite id="F17" />

The Usage and Cost Analytics API, Claude API OTel spans, Claude Code traces, and Managed Agents are beta; tier spend caps (`$500` Start, `$1,000` Build, `$200,000` Scale) are pricing policy.<Cite id="F13 F20 F21 F22 F30" /> Beta header values, attribute names, and cap amounts change; re-verify them.

</Callout>

Run the two speeds separately: page on OTel counters or the legacy `/cost_report` (`~5m` lag), and reconcile chargeback in the Analytics API across workspace, agent, actor, and context-window dimensions, accepting its 4-to-24-hour lag.<Cite id="F16 F18" /> 
A **dashboard** groups measurements for investigation. Show request volume beside error ratios and burn windows, TTFT and full-turn percentiles, token input/output and cache-read share, cost per successful task, and sampled quality scores. Break down by model, workspace, and deployment where available. Compare each series with its baseline and mark releases; use the same denominators in panels and alerts. Separate estimated live spend from reconciled reports and display data freshness.

## Alert rules and routing

The alert is arithmetic on the error budget; the window pairing helps distinguish sustained burn from a transient spike. The following runnable Python example uses precomputed error ratios for a `99.9%` 30-day completion SLO:

```python
def evaluate_slo_alerts(
    err_rate_5m: float,
    err_rate_30m: float,
    err_rate_1h: float,
    err_rate_6h: float,
    err_rate_3d: float,
    slo: float = 0.999,
) -> str:
    budget = 1.0 - slo
    if (err_rate_1h > 14.4 * budget) and (err_rate_5m > 14.4 * budget):
        return "PAGE_CRITICAL_14.4X"
    if (err_rate_6h > 6.0 * budget) and (err_rate_30m > 6.0 * budget):
        return "PAGE_HIGH_6X"
    if (err_rate_3d > 1.0 * budget) and (err_rate_6h > 1.0 * budget):
        return "TICKET_SLOW_BURN_1X"
    return "OK"
```

Consider steady traffic and no earlier errors. At 14:00 a deploy causes a `0.018` failure ratio. The five-minute burn reaches `18x`; the one-hour ratio exceeds `0.0144` just after 14:48, triggering the critical page. Roll back at 14:55: once the five-minute ratio falls below the threshold, that alert clears even if the one-hour ratio remains high. This example assumes uniform traffic, no measurement delay, and the critical rule considered in isolation; the 6x rule can page earlier.<Cite id="F4 F5" />

Route severity by burn tier and send other signals to the team that can act on them; thresholds below are illustrative except the burn-rate pairs.<Cite id="F4 F5" />

| Condition | Trigger | Route | Triage |
|---|---|---|---|
| Fast availability burn | `14.4x` in `1h` AND `5m`<Cite id="F5" /> | Page | Outage; compare `stop_reason` mix to baseline<Cite id="F11" /> |
| Sustained burn | `6x` in `6h` AND `30m`<Cite id="F5" /> | Page | Sustained errors or `max_tokens` spikes; check deploys<Cite id="F11" /> |
| Slow burn | `1x` in `3d` AND `6h`<Cite id="F5" /> | Ticket | Tail-latency creep or ramp-limit bursts<Cite id="F31" /> |
| Spend cap or limit hit | `429 enforced_spend_limit_reached` or `400` limit<Cite id="F30" /> | Page | Check which limit was reached and raise it or wait for its reset<Cite id="F30" /> |
| Hourly spend spike | Workspace spend over 3x its 7-day baseline (application telemetry or `/cost_report`)<Cite id="F16" /> | Page (prod) / Ticket (dev) | Investigate the workspace and correlate with application key usage |
| Refusal spike | Refusal rate over 4x its budget<Cite id="F12" /> | Page / Ticket | Read `stop_details.category`, compare prompts, traffic, and serving changes<Cite id="F12 F28" /> |
| Tool failure spike | Over 10% failures on one tool or MCP server<Cite id="F19" /> | Page (critical) / Ticket | Group by `tool_name` and `error_type`<Cite id="F19" /> |
| Cache hit drop | Large sustained fall in cache-read share<Cite id="F23" /> | Ticket (page if ITPM `429`s) | Enable `diagnostics.previous_message_id`<Cite id="F24" /> |
| Quality drift | Online eval falls a few points<Cite id="F26" /> | Ticket | Review transcripts; check retrieval<Cite id="F26" /> |
| Deprecated model active | Any calls inside the notice window<Cite id="F29" /> | Ticket | Audit by model, migrate before retirement<Cite id="F29" /> |

## Anomalous usage and spend limits

Spend limits fail in two ways, and the difference decides what retries can do. Hitting a monthly tier cap — `$500` on Start, `$1,000` on Build, `$200,000` on Scale — returns HTTP `429 rate_limit_error` with `enforced_spend_limit_reached` and no `retry-after`, until the next UTC month unless a higher limit is granted.<Cite id="F30" /> Hitting a spend limit you configured for the organization or workspace returns HTTP `400` with `invalid_request_error` (Claude Code workspaces may return `429`), and Console can email alerts on those limits.<Cite id="F30 F32" /> A **ramp limit** differs: it caps how fast token usage on a model may grow, so after a sharp increase requests return `429` with `error.details.error_code: ramp_limit_exceeded` even below the nominal ITPM and OTPM limits.<Cite id="F31" /> For ramp limits, reduce the rate of increase and follow any `retry-after` guidance. Include the error code in the alert payload.<Cite id="F31 F30" />

Isolation comes from workspaces: a workspace (`wrkspc_...`) holds its own API keys, monthly spend limits, spend-alert emails, and per-model rate limits, and every authenticated response returns `anthropic-workspace-id` — the field to group spend alerts on.<Cite id="F32" /> For Claude Enterprise organizations only, not Console organizations, the Spend Limits API reads each member's resolved effective limit and period-to-date spend and manages per-user overrides and limit-increase requests.<Cite id="F33" />

## Drift after model updates

Automated evals are useful pre-launch and in CI/CD; production monitoring detects distribution drift and unanticipated real-world failures after launch, alongside transcript review.<Cite id="F26" /> Compare sampled live outcomes with a baseline by task and traffic cohort. Review failing transcripts and retrieval results; validate any judge against human labels before relying on its score. After a model or prompt rollout, compare the canary with the previous version and roll back if the regression is material. Model identity explains some drift and rules out the rest. From Claude 4.6 onward, a dateless ID such as `claude-sonnet-4-6` or `claude-sonnet-5` maps to a single fixed snapshot whose weights and configuration Anthropic does not change, whereas pre-4.6 models used dated snapshots like `claude-sonnet-4-5-20250929` plus optional aliases like `claude-sonnet-4-5`.<Cite id="F27" /> Pinning weights does not freeze behavior: serving infrastructure — request router, safety classifiers, sampling logic — can change.<Cite id="F28" /> Anthropic describes Active, Legacy, Deprecated, and Retired lifecycle stages and gives customers with active deployments at least 60 days' notice before retirement of publicly released models. Amazon Bedrock and Google-managed Vertex AI maintain separate schedules.<Cite id="F29" />

Two incidents look alike but differ. A token-cost jump with ITPM `429`s and flat traffic can indicate a cache miss. Check `usage.cache_read_input_tokens`: cache reads are billed at a discounted rate and excluded from default cache-aware ITPM limits, so misses can increase cost and rate-limit pressure.<Cite id="F23 F34" /> Opt into diagnostics on both requests: send `diagnostics.previous_message_id` as null on the first and the previous response ID on the next. Diagnostics can identify the first structural divergence; expiry and minimum cacheable length can also cause misses.<Cite id="F35" /> A refusal or style shift on a pinned `4.6+` ID can reflect serving infrastructure, prompt, or traffic changes; investigate before assigning a cause.<Cite id="F27 F28" />

For a planned migration: validate with a regression suite on `pass^k`,<Cite id="F25" /> canary the `stop_reason` mix and token ratios, pin explicit model IDs rather than aliases,<Cite id="F27" /> and keep refusal rate and transcript sampling running to detect changes on frozen IDs.<Cite id="F12 F28" />

## Decision criteria

Pick the signal by the question on call.

1. **Is the service up?** Completion yield from status codes plus `stop_reason`, alerted with MWMBR pairs.<Cite id="F5 F11" />
2. **Is it fast enough?** Streaming TTFT percentiles, then end-to-end latency separately; tune `output_config.effort` as targets tighten.<Cite id="F7 F8" />
3. **Is it answering well?** Refusal rate, tool failure rate, `pass^k`, and grounded-answer rate, from response fields, tool events, and evaluated samples.<Cite id="F10 F12 F19 F25" />
4. **Is spend abnormal now?** Application counters or the legacy `/cost_report` at typical `~5m` freshness, grouped by workspace where available.<Cite id="F16 F18 F32" />
5. **Who owes this month's bill?** The Analytics API with `ending_at` pinned to `data_refreshed_at`, after reconciliation.<Cite id="F14 F15" />
6. **Did a model change cause it?** Line behavior history up against deploy timestamps; check `stop_reason` mix and cache reads first.<Cite id="F27 F28" />

Before choosing a threshold, collect: requests per window (a quiet endpoint may need a different alerting approach),<Cite id="F6" /> the `stop_reason` distribution,<Cite id="F11" /> cache-read share,<Cite id="F23" /> and the plane that produced the number.<Cite id="F21" />

## Failure modes and recovery

Start by checking whether the alert classified the outcome correctly and whether its data is fresh.

<Callout type="mistake" title="Alerting only on HTTP 4xx and 5xx">

Refusals, `max_tokens` truncations, and `model_context_window_exceeded` stops arrive as HTTP `200` responses carrying `stop_reason`,<Cite id="F11 F12" /> and Claude Code logs refusals as `claude_code.api_refusal`, not `claude_code.api_error`.<Cite id="F19" /> Classify each termination by the task: `tool_use` can be a normal intermediate step, while unhandled truncation may be a failure.

</Callout>

<Callout type="mistake" title="Paging in real time on the Analytics API">

Analytics data typically refreshes within 4 hours and can take up to 24, and values move until about 7 days after month end.<Cite id="F14" /> A runaway agent loop can escape timely detection there, and previously reported values can be revised. Page on OTel metrics or the legacy `/cost_report`; keep the Analytics API for reconciled reports.<Cite id="F16 F18" />

</Callout>

<Callout type="mistake" title="Treating a dateless 4.6+ ID as a rolling alias">

`claude-sonnet-4-6` and `claude-sonnet-5` are pinned snapshots with fixed weights,<Cite id="F27" /> so an unexplained behavior change is not a silent upgrade. Router, classifier, and sampling changes can affect behavior on a pinned ID,<Cite id="F28" /> so compare model IDs and deployments, run regressions, and review transcripts.

</Callout>

Script two recoveries. When cache hit rate falls, confirm with `usage.cache_read_input_tokens`, then use cache diagnostics to investigate possible prefix changes. Check expiry, traffic, and other possible causes too.<Cite id="F35" /><Cite id="F23 F24" /> When a spend alert fires, read the status code: `400 invalid_request_error` is a limit you set and can raise, `429` with `enforced_spend_limit_reached` requires a higher tier or the next monthly reset, and `ramp_limit_exceeded` describes the shape of the traffic change, not its level.<Cite id="F30 F31" />

<ExamLens>

- Noisy pages plus a missed slow leak is an MWMBR fix: page on `1h/5m` at `14.4x` and `6h/30m` at `6x`, ticket on `3d/6h` at `1x`, and widen windows or add synthetic traffic on quiet endpoints.<Cite id="F4 F5 F6" />

- Cost growth plus ITPM `429`s on flat traffic warrants checking cache reads and diagnostics; changes on a pinned `4.6+` ID warrant checking prompts, traffic, and serving infrastructure.<Cite id="F23 F24 F27 F28" />

</ExamLens>
