**Identity** is the principal, a person or workload, whose permissions govern an API request or tool action. Track the workload calling Claude, the user on whose behalf a tool acts, and the records that prove what happened. **Workload identity federation** (WIF) exchanges a workload's short-lived OpenID Connect (OIDC) token for a short-lived Anthropic token, replacing a long-lived Anthropic API key for that workload. **Model Context Protocol (MCP)** is the protocol agents use to connect to external tools and data servers; keep a workload's Claude identity separate from a user's delegated MCP identity.<Cite id="F5 F18" />

## How a Claude workload gets an identity

Claude API authentication has three mechanisms: API keys, Workload Identity Federation, and App Attest.<Cite id="F1" /> A **service account** is a named, non-human identity for an Anthropic workload.<Cite id="F54" /> A WIF rule maps a matching upstream identity to the selected account.<Cite id="F5 F7" /> The default WIF scope, `workspace:developer`, grants the same access as a workspace API key; a rule can use a different scope where supported.<Cite id="F8 F51 F53" />

Scope causes the first class of failures. A workspace-scoped key works only in that workspace and its requests may omit the workspace ID.<Cite id="F2" /> An unscoped key must send `anthropic-workspace-id` on every request; a missing header returns HTTP 400 `invalid_request_error`, and an inaccessible or unknown workspace returns 404 `not_found_error`.<Cite id="F2 F3" /> Anthropic service accounts are non-human principals: each starts in the default workspace, you add one to each further workspace it should reach, and at exchange time the rule's workspace must match one of its memberships, with usage following that workspace's limits and attribution.<Cite id="F7" />

**The Admin API** manages organization resources and accepts an Admin API key, an `org:admin` OAuth bearer token, or an unscoped personal or service-account key. Workspace-scoped keys cannot call it; service-account, federation-issuer, and federation-rule endpoints require `org:admin` specifically.<Cite id="F4" />

| Credential | Transport | Reaches |
|---|---|---|
| Workspace-scoped API key | `Authorization: Bearer` (SDK reads `ANTHROPIC_API_KEY`) | That workspace only; workspace ID may be omitted<Cite id="F2" /> |
| Unscoped API key | Same, plus `anthropic-workspace-id` per request | Any workspace you name, else 400/404<Cite id="F3" /> |
| Federated token `sk-ant-oat01-...` | `Authorization: Bearer` | Claude API access granted by the matched rule's OAuth scope<Cite id="F5 F8" /> |
| Admin API key `sk-ant-admin...` | `x-api-key` | Admin API; Activity Feed if its scope was enabled at key creation<Cite id="F4 F28 F50" /> |
| `org:admin` OAuth token | `Authorization: Bearer` | Admin API plus identity and federation management<Cite id="F4" /> |

## Workload identity federation

WIF binds an upstream OIDC issuer and a claim-matching rule to a named Anthropic service account. The workload presents a signed JWT from its identity provider, Anthropic validates it against the trust rules you configure in the Claude Console, and the response is a short-lived Anthropic access token bound to that account. Supported upstream sources include AWS, Google Cloud, Entra ID, GitHub Actions, Kubernetes, SPIFFE, and Okta.<Cite id="F5 F6" />

The SDK posts the JWT to `POST /v1/oauth/token` using the RFC 7523 jwt-bearer grant.<Cite id="F6" /> The request includes `grant_type`, `assertion`, `federation_rule_id`, and `organization_id`; `service_account_id` is optional and, if supplied, must match the rule's target account.<Cite id="F36 F37" />

A rule sets the OAuth scope and token lifetime. The default scope `workspace:developer` grants workspace API-key access, and `token_lifetime_seconds` ranges from 60 to 86,400 seconds with a 3,600-second API default.<Cite id="F8 F51 F53" /> The wizard prefills 600 seconds.<Cite id="F42" /> The client chooses a rule by ID; Anthropic does not search rules implicitly.<Cite id="F41" />

The direct environment-variable path requires `ANTHROPIC_FEDERATION_RULE_ID`, `ANTHROPIC_ORGANIZATION_ID`, and either `ANTHROPIC_IDENTITY_TOKEN_FILE` or `ANTHROPIC_IDENTITY_TOKEN`.<Cite id="F9" /> The SDK also reads `ANTHROPIC_WORKSPACE_ID`, but the environment path activates without it. The exchange requires `workspace_id` when the rule covers multiple workspaces; the service account is selected by the rule.<Cite id="F37 F43" /> Prefer file-mounted projected tokens where available. Constructor credentials and `ANTHROPIC_API_KEY` / `ANTHROPIC_AUTH_TOKEN` precede federation, so either can override it. Remove them during migration and confirm which credential the SDK resolved.<Cite id="F10" />

Two clocks run at once. A minted token expires at the lesser of the rule lifetime and twice the upstream JWT's remaining lifetime, never below 60 seconds.<Cite id="F40" /> The SDK starts an advisory refresh at expiry minus 120 seconds and rereads `ANTHROPIC_IDENTITY_TOKEN_FILE` on every exchange, which is how rotated Kubernetes projected tokens get picked up.<Cite id="F11 F35" />

Runnable with a current anthropic Python SDK that supports WIF, the environment variables above, and a projected OIDC token file.<Cite id="F5" />

```python
from anthropic import Anthropic

client = Anthropic()  # resolves WIF credentials; no ANTHROPIC_API_KEY
message = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=600,
    messages=[{"role": "user", "content": "Check order status."}],
)
```

## Claude Code and cloud-provider credentials

Claude Code aimed at a cloud provider authenticates to that provider, not to the Claude API. `CLAUDE_CODE_USE_BEDROCK=1` selects the default AWS SDK credential chain, including instance-profile and task credentials, and `awsAuthRefresh` runs a command such as `aws sso login --profile myprofile` only after the current credentials fail an STS check.<Cite id="F12 F13" /> Google Cloud's Agent Platform accepts Application Default Credentials from `gcloud`, a service-account key file, or credentials already in the environment.<Cite id="F14" /> With `CLAUDE_CODE_USE_FOUNDRY=1` you can use an API key, Entra ID through the Azure SDK default credential chain, or a supplied Entra token in `ANTHROPIC_FOUNDRY_AUTH_TOKEN`, sent as `Authorization: Bearer` and preferred over the other two.<Cite id="F15" />

`apiKeyHelper` in settings JSON runs a command through the system shell and sends its stdout as both `X-Api-Key` and `Authorization: Bearer`.<Cite id="F16" /> Output is cached five minutes by default, the interval is `CLAUDE_CODE_API_KEY_HELPER_TTL_MS` in milliseconds, and the helper re-runs after an Anthropic API 401 or 403.<Cite id="F17" /> Provider-native IAM authorizes a cloud inference API, not an Anthropic workload principal, so it is not a substitute for WIF.

## Least privilege for tools and MCP

**Least privilege** gives each identity and tool only the access needed for its task. Tool declarations define what the model may request, permission rules decide which requested actions proceed, Model Context Protocol (MCP) server authorization checks the delegated token and its audience, and backend authorization still checks tenant and object ownership. An allowlisted tool is not authorization to every record that tool can reach.

Claude Code permission rules live under `permissions.allow`, `permissions.ask`, and `permissions.deny`, with patterns such as `Bash(npm run lint)` and `Read(./.env)`; use managed settings for organization-enforced policy and project settings for shared team rules.<Cite id="F22 F45" /> In the Agent SDK, `allowedTools` / `disallowedTools` (TypeScript) and `allowed_tools` / `disallowed_tools` (Python) only add entries to those allow and deny lists. Unlisted tools stay available and fall through to the permission mode, so pair a tight allow list with `dontAsk` when a headless agent must deny anything requiring an unlisted approval.<Cite id="F33" />

MCP's HTTP authorization model lets clients call restricted servers on behalf of resource owners.<Cite id="F18" /> For HTTP, send bearer tokens in the `Authorization` header on every request and never in query strings.<Cite id="F39" /> For stdio, implementations should retrieve credentials from the environment.<Cite id="F47" /> An MCP server must validate that an access token was issued for it as the intended audience, and must not accept or transit another token. An upstream call uses a separate token issued for that resource.<Cite id="F19 F20" />

The Messages MCP connector takes a remote server's `type: "url"`, `url`, `name`, and optional `authorization_token`.<Cite id="F44" /> The API consumer obtains and refreshes that access token before the API call.<Cite id="F21" /> Treat it as a sensitive request credential; do not put it in prompt text or supply a refresh token in its place.

**A secrets manager** stores credentials outside application code and supplies them to workloads at runtime. Anthropic recommends storing API keys in one, rotating them periodically, and disabling or deleting a key you suspect has leaked.<Cite id="F30" /> Keep secrets out of prompts, `CLAUDE.md`, tool descriptions, examples, committed settings, and logs. Claude Code loads `CLAUDE.md` instructions into context at the start of each session, so inject secret values at runtime instead.<Cite id="F38" /> When rotating a Compliance Access Key, create a replacement with the same scopes, update and verify the integration, then delete the old key.<Cite id="F31" /> Revoke a leaked credential immediately and investigate its use, accepting that revocation can interrupt live workloads.

## Audit logging of security-relevant actions

Two audit sources cover different planes, and neither is a complete execution trace. In Claude Code **OpenTelemetry (OTel)**, set `CLAUDE_CODE_ENABLE_TELEMETRY=1` with `OTEL_LOGS_EXPORTER=otlp`: `claude_code.tool_decision` records an accept or reject permission outcome with the tool name and `tool_use_id`, while `claude_code.tool_result` records completed execution and is not emitted for a rejected call.<Cite id="F23 F48 F52" /> Events join on `prompt.id` for prompts and actions, on `tool_use_id` for decision and result pairs, and on `session.id` for sessions.<Cite id="F46 F52" /> Direct API-key and cloud-provider sessions populate only `user.id` and `session.id`, and `user.id` is installation-scoped, so attach the real human or workload identity per launch through `OTEL_RESOURCE_ATTRIBUTES` with values such as `enduser.id` and `tenant.id`.<Cite id="F24" /> MCP server and tool names and their arguments appear only with `OTEL_LOG_TOOL_DETAILS=1`, which raises the content sensitivity of the collector.<Cite id="F25" />

The Compliance API Activity Feed covers the organization plane. Query `GET /v1/compliance/activities` with an `x-api-key` credential and `anthropic-version`; a read-only audit collector needs the `read:compliance_activities` scope.<Cite id="F26 F50" /> API-key calls appear as the `api_actor` type carrying `api_key_id`, IP address, and user agent. Admin API keys can read only the Activity Feed, while Compliance Access Keys cover additional endpoints according to scope.<Cite id="F27 F28" /> The feed excludes prompt text and model responses from API-key Claude API workloads, and it excludes Claude Code usage authenticated with a Claude Console API key, run through any cloud platform, or run in a Claude Code cloud session; route those paths through OTel or your own records.<Cite id="F29 F34" />

| Question | Use | Not enough on its own |
|---|---|---|
| Was this tool call permitted or rejected? | `claude_code.tool_decision`, joined by `tool_use_id`<Cite id="F23" /> | `tool_result`, which omits rejected calls<Cite id="F23" /> |
| Who is behind an API-key session? | `OTEL_RESOURCE_ATTRIBUTES` you set per launch<Cite id="F24" /> | `user.id`, which is installation-scoped<Cite id="F24" /> |
| Which key made an admin or API call? | Activity Feed `api_actor` with `api_key_id`<Cite id="F27" /> | Admin keys, which reach the Activity Feed only<Cite id="F28" /> |
| What did a Bedrock Claude Code session do? | Claude Code OTel plus application logs<Cite id="F23 F29" /> | Compliance Feed, which excludes those sessions<Cite id="F29" /> |
| Was this record in the caller's tenant? | Your application's authorization audit record | Model transcript or activity entry |

Give each source one job: OTel for prompt-to-tool reconstruction and permission outcomes, the Feed for organization and actor events, and application audit records for server-side Messages API tools, carrying the authenticated principal, tenant, session or request ID, tool name, authorization result, and resource IDs. Neither a compliance entry nor a model transcript alone proves downstream business authorization.

## Decision criteria

Choose the principal by the execution boundary, then name the evidence you will demand before calling a migration done.

| Situation | Choose | Evidence to check |
|---|---|---|
| Backend calls the Claude API, platform issues OIDC tokens | Service account plus narrow WIF rule<Cite id="F5 F7" /> | Exchange success, rule ID in logs, no `ANTHROPIC_API_KEY` in the environment<Cite id="F10" /> |
| Claude Code against a cloud provider | That provider's credential chain<Cite id="F12 F14 F15" /> | STS or ADC validation, not a Claude key |
| Gateway or short-lived runner needs rotating credentials | `apiKeyHelper` with an explicit TTL<Cite id="F16 F17" /> | 401/403 refresh observed at the gateway |
| Agent classes differ in permission or audit owner | One service account per trust boundary, separate rules per environment, smallest usable scope<Cite id="F7 F8" /> | Rule subject and claim constraints, workspace membership |
| Tool acts on a user's own records | Per-user delegated MCP token validated by the server<Cite id="F18 F19" /> | Audience, issuer, expiry, scopes, object ownership |
| Headless agent must deny anything unapproved | Tight allow list plus `dontAsk`<Cite id="F33" /> | Unlisted tools still reach the permission mode<Cite id="F33" /> |

Keep `org:admin` away from inference calls and use `workspace:developer` only where the workload needs that endpoint family. Map workload classes to distinct service accounts and narrow rules, assign only the workspaces each account needs, and bound exchanges with claim and subject constraints such as environment, cluster namespace, or CI repository.<Cite id="F7 F8" /> Rotation is an overlap deployment: issue the replacement, distribute it by secret injection, confirm authentication and attribution, then revoke. With WIF, stage the issuer, rule, and service account first, remove higher-precedence keys, confirm WIF is live, and delete old keys last.

## Failure modes and recovery

<Callout type="mistake" title="Federation configured, API key still winning">

Because `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` outrank the federation tiers, a leftover key means every request still uses the static credential while the WIF rule looks healthy. Unset both, then confirm the credential source before you judge the rule.<Cite id="F10" />

</Callout>

<Callout type="mistake" title="The MCP server forwards the token it received">

Accepting a client token and replaying it against a downstream resource breaks audience binding and lets one surface grant access on another. Validate that the token was issued for this server, reject anything else, and mint a separate token for the upstream resource.<Cite id="F19 F20" />

</Callout>

<Callout type="mistake" title="Reading the Compliance Feed as an execution trace">

The Feed does not carry API-key workload prompts and responses, and it omits Claude Code sessions using a Claude Console key, a cloud platform, or a cloud session. Assume the gap and fill it with OTel events and application audit records.<Cite id="F29 F34" />

</Callout>

Three smaller traps follow. A projected token that lags the SDK's refresh schedule is not repaired by Claude's own token refresh, because rereading the file is the mechanism, not the cure.<Cite id="F11 F35" /> Workspace-scoped keys and service accounts fail outside their memberships, and a workspace key never reaches the Admin API.<Cite id="F2 F4 F7" /> Treating MCP OAuth as authentication alone skips the checks that actually gate data: audience, issuer, scopes, user delegation, and object-level tenant authorization.<Cite id="F18 F19" />

## Exam lens

<ExamLens>

- WIF "enabled" but requests still attributed to a key: check credential precedence and remove the lingering `ANTHROPIC_API_KEY` before judging the rule.
- An MCP server accepting a Claude API bearer token and forwarding it downstream: reject token passthrough, validate audience, obtain a downstream token.
- A broad allow list letting a tool touch another tenant's record: separate model and tool permission from per-user, per-tenant authorization in the server.
- A security team expecting the Compliance API to show Claude Code tool calls over Bedrock or a Console key: those events belong to OTel and application logs.

</ExamLens>

## Self-check

<SelfCheck question="Why can WIF be fully configured and still not be used?">

A constructor credential or `ANTHROPIC_API_KEY` / `ANTHROPIC_AUTH_TOKEN` wins earlier in SDK credential precedence. Unset them and confirm which credential source the SDK resolved.<Cite id="F10" />

</SelfCheck>

<SelfCheck question="What proves a Claude Code tool call was denied, and how do you tie it to the rest of the session?">

`claude_code.tool_decision` records the accept or reject outcome with `tool_use_id`; `claude_code.tool_result` covers only executed calls. Join on `tool_use_id`, then widen with `prompt.id` and `session.id`.<Cite id="F23 F24" />

</SelfCheck>

<SelfCheck question="May an MCP server reuse the bearer token it received for a downstream API call?">

No. It validates that token as intended for itself, per RFC 8707 audience binding, and must not accept or transit other tokens; the downstream call needs a token issued for that resource.<Cite id="F19 F20" />

</SelfCheck>
