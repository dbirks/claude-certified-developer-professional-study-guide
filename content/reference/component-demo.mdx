## Error handling basics

Treat HTTP 429 as a rate-limit response and delay the next attempt. A `max_tokens` stop is different: the request succeeded, but the answer may be incomplete. Inline code such as `stop_reason` and `anthropic.RateLimitError` uses the monospace font.

### Classification table

| Signal | Layer | Retry? | Action |
|---|---|---|---|
| HTTP 429 `rate_limit_error` | Transport | Yes, with backoff | Honor `retry-after` header |
| HTTP 529 `overloaded_error` | Transport | Yes, bounded | Back off; consider fallback model |
| `stop_reason: "max_tokens"` | Response | No (same request) | Raise `max_tokens` or continue |
| `stop_reason: "refusal"` | Response | No | Route to safety-handling path |

### Retry sketch

```python
import random, time
import anthropic

client = anthropic.Anthropic(max_retries=0)  # we own retries here

def call_with_backoff(request: dict, attempts: int = 4) -> anthropic.types.Message:
    for attempt in range(attempts):
        try:
            return client.messages.create(**request)
        except anthropic.RateLimitError as err:
            delay = float(err.response.headers.get("retry-after", 2 ** attempt))
        except anthropic.InternalServerError:
            delay = min(30, 2 ** attempt) * random.uniform(0.5, 1.5)
        time.sleep(delay)
    raise RuntimeError("retry budget exhausted")
```

## Callouts and exam lens

<Callout type="mistake" title="Retrying a refusal">
Retrying a `refusal` repeats the refusal at extra cost. Route it to a safety-handling path instead.
</Callout>

<Callout type="version" title="Checked 2026-11-19">
Rate-limit header names and SDK retry defaults change between releases. Re-check before you rely on them.
</Callout>

<Callout type="note" title="Note">
A neutral note callout with a [link to the docs](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons).
</Callout>

<ExamLens>
When a scenario mixes several failure signals in one retry path, the better answer usually **branches on the signal**: back off on rate limits, change the request on length stops, and route refusals elsewhere.
</ExamLens>

## Self-check

<SelfCheck question="Why can an HTTP 200 response still be an application failure?">
The request succeeded at the transport layer, but `stop_reason` may be `max_tokens` or `refusal`, so the content can be incomplete or absent.
</SelfCheck>

<SelfCheck question="Which signal should never be retried unchanged?">
A length stop (`max_tokens`): the same request will truncate again.
</SelfCheck>
