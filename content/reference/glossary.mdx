This glossary defines service health, Claude API, evaluation, and capacity terms. Its formulas use illustrative numbers; check current documentation for prices, cache limits, and SDK defaults.

## Service health and telemetry

An **SLI (service-level indicator)** is a measured signal of customer-relevant service behavior. SRE guidance recommends writing it as a ratio of two counts: the number of good events divided by the total number of events, for example successful HTTP requests over total HTTP requests.<Cite id="F2" /> A **SLO (service-level objective)** adds two pieces to that indicator: a performance goal and a period over which the goal is evaluated against the indicator.<Cite id="F1" /> Two common SLIs are availability, the proportion of successful requests, and latency, the proportion of requests faster than a defined threshold.<Cite id="F21" />

An **SLA (service-level agreement)** is a contract with the customer or provider that carries stated remedies or consequences; treat it as legal wording sitting on top of your SLOs, not as the engineering target itself. Decide what counts as a good event before you calculate anything: for Claude-backed work you must state how refusals, failed tool sequences, cancellations, and invalid requests enter the denominator, because an HTTP-successful request can still be a refused or incomplete answer.

### Objectives and budgets

| Term | Definition |
|---|---|
| **SLI** | A measured signal of service behavior; often expressed as good events divided by total events.<Cite id="F2" /> |
| **SLO** | An SLI plus a performance goal plus an evaluation period.<Cite id="F1" /> |
| **SLA** | Commitment with defined remedies; a contract, while the SLO is the engineering target. |
| **Availability SLI** | Proportion of successful requests.<Cite id="F21" /> |
| **Latency SLI** | Proportion of requests faster than a defined threshold.<Cite id="F21" /> |
| **Request-based SLI** | SLI whose events are requests: good requests divided by eligible total requests.<Cite id="F2" /> |
| **Window-based SLI** | Ratio of good time windows to eligible time windows; define the criterion for a good window. |
| **Error budget** | Bad-event fraction the SLO permits; a 99.9% objective permits a constant 0.1% error rate.<Cite id="F3 F4" /> |
| **Burn rate** | How fast, relative to the SLO, the service consumes its error budget.<Cite id="F3" /> A constant burn rate of 1 uses the whole budget over the SLO window.<Cite id="F4" /> |
| **Rolling window** | Evaluation interval that advances continuously, unlike a calendar-aligned reporting period. |
| **Good event / bad event** | The two sides of an SLI contract: an event that satisfies or violates the stated success definition. |

### Telemetry primitives

| Term | Definition |
|---|---|
| **Metric** | A measurement of a service captured at runtime that you can aggregate across events.<Cite id="F34" /> |
| **Counter** | Monotonically accumulating measurement; a good fit for requests, errors, token counts, and completed tasks. |
| **Gauge** | Point-in-time reading that can rise and fall, such as active queue depth or in-flight calls. |
| **Histogram** | Metric instrument intended for statistically meaningful values such as summaries and percentiles, so keep one for latency instead of an average alone.<Cite id="F22" /> |
| **Trace** | Linked view of one request's path through your components; for agents include model turns, tools, retrieval, and retries. |
| **Span** | A timed parent-child segment inside a trace, such as one Messages API call or one tool invocation. |
| **Structured log** | Event record with stable machine-readable fields such as request ID, model, `stop_reason`, token usage, and outcome. |
| **Cardinality** | Number of distinct label combinations across time series; avoid unbounded label values such as prompt text, user IDs, or tool arguments. |
| **Golden signal** | A summary health signal such as latency, traffic, errors, or saturation; pair these with task quality and token cost for Claude workloads. |

## Messages API and agent execution

The Messages API is stateless: you always send the full conversational history with the request, so no prior turns are held as server-side conversation state for you.<Cite id="F19" /> Your application therefore owns the loop: it sends history, reads the response, runs tools, and decides whether to call again. Two response fields drive that decision. `stop_reason` says why generation ended, and the usage block reports token counts used in cost calculations.<Cite id="F36 F38" />

Every successful Messages API response includes a `stop_reason` field that tells you why Claude stopped generating; check it to decide whether to use the response as-is, continue the conversation, retry, or fall back to another model.<Cite id="F17" /> Documented values include `end_turn`, `max_tokens`, `stop_sequence`, `tool_use`, `pause_turn`, `refusal`, and `model_context_window_exceeded`.<Cite id="F36" /> In a stream, `stop_reason` is initially null; inspect the completed response.<Cite id="F36 F39" />

### Stop reasons and what to do with them

- **`end_turn`** — Claude completed its response naturally; use the response.<Cite id="F18" />
- **`max_tokens`** — Output reached its token limit; treat it as potentially truncated, then continue or raise the budget.<Cite id="F36" />
- **`tool_use`** — Claude handed control to a tool call; execute the tool, return the result, then expect the model's next turn.<Cite id="F36" />
- **`pause_turn`** — A server-tool loop reached its iteration limit. To continue, append the unchanged assistant content, keep the same tools, and do not append a user message; reuse the container ID if present.<Cite id="F36" />
- **`refusal`** — Claude declined to respond; inspect `stop_details` and apply your safety-handling policy.<Cite id="F36" />
- **`stop_sequence`** — A configured stop string ended generation; inspect `stop_sequence` to see which fired.<Cite id="F36" />
- **`model_context_window_exceeded`** — The response filled the model's context window; treat the output as truncated.<Cite id="F36" />

### Execution terms

| Term | Definition |
|---|---|
| **Messages API** | Claude's direct model prompting API; the application orchestrates any custom agent loop itself.<Cite id="F19" /> |
| **Stateless conversation** | Each request carries the history the current turn needs; the API keeps no conversation between calls.<Cite id="F19" /> |
| **Assistant turn** | One model response cycle: text, tool calls, or a stop condition, not necessarily a finished user task. |
| **Streaming** | Messages API responses arrive incrementally as server-sent events, including text and tool-use deltas, so you can consume output before the response completes.<Cite id="F9" /> |
| **`message_start`** | Opening stream event carrying an initial Message object with empty content; treat it as pre-completion.<Cite id="F39" /> |
| **`message_delta`** | Stream event carrying response changes whose usage counts are cumulative, so do not sum event snapshots as if they were deltas.<Cite id="F10" /> |
| **Tool round-trip** | The model's tool request, your execution, the tool-result submission, and the model's following response; attribute latency and tokens across all four. |
| **Agent loop** | Application-controlled repetition of model calls, tool runs, and state updates until a stop condition or task policy ends the work. |
| **Orchestration overhead** | Latency, tokens, and infrastructure spent on routing, tools, retries, and control logic beyond a single generation. |

## Tokens, caching, price, and latency

The usage fields are the least intuitive part of Claude cost accounting. When caching is used, `input_tokens` represents tokens after the last cache breakpoint, not all the input tokens sent.<Cite id="F12" /> Total input is `cache_read_input_tokens + cache_creation_input_tokens + input_tokens`.<Cite id="F11" /> Read that sum, not `input_tokens`, whenever you compute a cache percentage or a per-request input volume.

Prompt caching reduces cost and latency by reusing previously processed portions of your prompt across API calls.<Cite id="F20" /> Writes cost more than plain input and reads cost less: a five-minute cache write is billed at 1.25x base input price, cache reads at 0.1x base input price on most models, and cache reads are charged when a subsequent request retrieves the cached content.<Cite id="F15 F14 F16" /> Minimum cacheable lengths and the multipliers both vary by model, so check the current prompt-caching and pricing pages before you set a threshold or forecast a bill.

For speed, keep three clocks apart: **TTFT (time to first token)** measures submission to first token;<Cite id="F7" /> **generation duration** measures first token to last token; and **end-to-end latency** measures task acceptance to your own completion event. Anthropic treats output tokens per second and time to first token as separate speed measures,<Cite id="F8" /> so report both rather than a single "latency" number.

### Token and cache terms

| Term | Definition |
|---|---|
| **Input tokens** | `input_tokens` reports uncached input after the last cache breakpoint.<Cite id="F12" /> |
| **Total input tokens** | `cache_read_input_tokens` plus `cache_creation_input_tokens` plus `input_tokens`.<Cite id="F11" /> |
| **Output tokens** | Tokens generated in the response; use the final cumulative usage count for throughput math.<Cite id="F10" /> |
| **Cache creation tokens** | `cache_creation_input_tokens` counts tokens written to the cache when creating a new entry.<Cite id="F13" /> |
| **Cache read tokens** | `cache_read_input_tokens` counts tokens retrieved from the cache; it is a volume, not a count of requests that hit.<Cite id="F38" /> |
| **Prompt caching** | Reuse of previously processed prompt portions across API calls.<Cite id="F20" /> |
| **Cache breakpoint** | Position that delimits the reusable prefix; everything after the last one lands in `input_tokens`.<Cite id="F12" /> |
| **Cache TTL** | Lifetime of a cached prefix; a five-minute write is valid for five minutes and the read duration follows the preceding write.<Cite id="F15 F14" /> |
| **Cache write multiplier** | 1.25x base input price for a five-minute cache write.<Cite id="F15" /> |
| **Cache read multiplier** | 0.1x base input price on most models.<Cite id="F14" /> |
| **Cache minimum length** | Shorter prompts cannot be cached, even when marked with `cache_control`; minimums are model-specific.<Cite id="F35" /> |
| **Cache hit (request-level)** | A request whose cache read count is above zero; it does not mean every cacheable token hit.<Cite id="F38" /> |
| **Cache hit rate (request-level)** | Requests with a nonzero cache read divided by cache-eligible requests; an application-defined ratio, not a field the API returns. |
| **Cache read share** | Cache-read input tokens divided by total input tokens processed; a volume metric.<Cite id="F11" /> |
| **Effective input cost** | Input spend after splitting ordinary input, cache writes, and cache reads and applying model rates and multipliers. |
| **Token price unit** | Prices are quoted per million tokens, so divide token counts by 1,000,000 before multiplying by a rate. |

### Speed and cost terms

| Term | Definition |
|---|---|
| **TTFT (time to first token)** | Time for the model to generate the first token of the response, measured from when the prompt was sent.<Cite id="F7" /> |
| **TTFB (time to first byte)** | Time until the first response byte reaches the client; includes transport and proxy effects, so it is not model TTFT. |
| **Generation duration** | First generated token to final generated token; isolate it from TTFT when you measure generation rate. |
| **Output tokens per second** | Output tokens divided by a stated measurement interval; distinguish generation throughput from TTFT.<Cite id="F8" /> |
| **End-to-end latency** | Accepted request or task to your application-defined completion, including queues, tools, retries, and model calls. |
| **p50 / median latency** | The 50th percentile, which is called the median; percentiles split ordered data into hundredths.<Cite id="F5" /> |
| **p95 latency** | The 95th-percentile estimate, with about 5% of observations above it.<Cite id="F5" /> |
| **p99 latency** | The 99th-percentile estimate: useful for tail behavior, noisier at small sample sizes.<Cite id="F5 F6" /> |
| **Tail latency** | Slow end of a latency distribution, usually assessed with p95/p99 instead of the mean. |
| **Cost per request** | Total metered cost divided by request count; it hides multi-turn work, failures, retries, and unequal task complexity. |
| **Cost per successful task** | Total cost for all attempts divided by tasks meeting the success criterion, so spend lines up with delivered work. |

## Reliability, evaluation, statistics, and queueing

A **retry** repeats a failed operation. Cap attempts. Google SRE recommends exponential backoff with jitter for remote-call retries to dampen error amplification.<Cite id="F29" /> On Claude, the official SDK already retries transient failures such as connection errors, rate limits, and 5xx server errors with exponential backoff, twice by default, honoring the `retry-after` header when present.<Cite id="F30" /> Instrument SDK retries and application retries separately, or you will read one as the other.

**Pass@k** is the probability that at least one of k generated samples passes the verifier; the original coding formulation checks whether any sample passes the unit tests.<Cite id="F33" /> **Pass^k** is the probability that all k trials succeed, and it cannot increase as k grows because demanding consistency across more trials is a harder bar.<Cite id="F31" /> Choose between them by the outcome you actually care about: selection among candidates versus repeated-run reliability.

**Precision** is true positives over true positives plus false positives; **recall** is true positives over true positives plus false negatives.<Cite id="F23 F37" /> **F1** is their harmonic mean, where precision and recall contribute equally,<Cite id="F24" /> which also means F1 does not represent asymmetric error costs. **Cohen's kappa** expresses agreement between two annotators as κ = (Po − Pe) / (1 − Pe), where Po is the observed agreement ratio and Pe is the agreement expected when both annotators assign labels randomly.<Cite id="F25" /> **Little's law** states that, under steady-state conditions, the mean number of items in a queueing system equals the mean arrival rate multiplied by the mean time an item spends in the system.<Cite id="F28" />

### Retries and overload

| Term | Definition |
|---|---|
| **Retry** | Repeated attempt after failure; cap attempts and use exponential backoff with jitter.<Cite id="F29" /> |
| **SDK retry default** | The official Claude SDK retries transient failures (connection errors, rate limits, 5xx) twice by default with exponential backoff, honoring `retry-after` when present.<Cite id="F30" /> |
| **Retry amplification** | Total provider attempts divided by original logical operations; 1.4x means 40% extra calls. |
| **Retry budget** | Cap on retry attempts or retry traffic per request or per window, so retries cannot crowd out normal work. |
| **Backpressure** | Slowing, rejecting, or queueing incoming work when downstream capacity is constrained; bound queue growth and signal overload. |

### Evaluation and statistics

| Term | Definition |
|---|---|
| **Pass@k** | Probability that at least one of k samples passes the verifier (unit tests in the original benchmark).<Cite id="F33" /> |
| **Pass^k** | Probability that all k trials succeed; it cannot increase as k increases.<Cite id="F31" /> |
| **Precision** | True positives divided by all positive predictions; in retrieval, relevant items among those returned.<Cite id="F23" /> |
| **Recall** | True positives divided by all actually relevant items; in retrieval, the share of relevant items retrieved.<Cite id="F37" /> |
| **F1** | Harmonic mean of precision and recall with equal relative contribution.<Cite id="F24" /> |
| **Recall@k** | Relevant items inside the first k results divided by all known relevant items for that query: coverage at a fixed context budget. |
| **Cohen's kappa (κ)** | Two-rater categorical agreement adjusted for chance agreement.<Cite id="F25" /> |
| **Observed agreement (Po)** | Fraction of examples where two raters chose the same category. |
| **Expected agreement (Pe)** | Agreement predicted from each rater's marginal label frequencies under independence.<Cite id="F25" /> |
| **Statistical power** | Probability a test rejects its null under a specified alternative; written 1 − β.<Cite id="F26" /> |
| **Minimum detectable effect (MDE)** | Smallest effect that, if true, has (1 − β) chance of producing a statistically significant estimate at the chosen α.<Cite id="F26" /> |
| **Type I / Type II error** | Type I is a false positive at rate α; Type II misses a real effect at rate β, whose complement is power. |
| **A priori power analysis** | Analysis done before the study, typically to estimate a sufficient sample size for adequate power.<Cite id="F27" /> |

### Queueing

| Term | Definition |
|---|---|
| **Arrival rate (λ)** | Mean tasks entering the queue per unit time; keep offered arrivals distinct from accepted or completed throughput.<Cite id="F28" /> |
| **In-flight work (L)** | Mean items inside the measured system boundary, including queued work when the queue is in scope.<Cite id="F28" /> |
| **Residence time (W)** | Mean time an item spends inside that boundary: queue wait plus service time when both are in scope.<Cite id="F28" /> |
| **Little's law** | Under steady state, mean in-system items equal mean arrival rate times mean time in system (L = λW).<Cite id="F28" /> |

## Operational formulas

Each formula names its units and its denominator. Numbers are illustrative arithmetic, not measured service data; prices and multipliers come from the 2026-11-19 documentation and change per model.

- **Request success SLI** = good requests ÷ eligible total requests. 9,980 ÷ 10,000 = 99.8%.<Cite id="F2" />
- **SLO compliance**: measured SLI ≥ target over the declared window. 99.8% measured against a 99.9% 30-day objective is below target for that window.<Cite id="F1 F4" />
- **Error budget** = 1 − SLO for a ratio SLO. 1 − 0.999 = 0.1%, and over 10,000 equally weighted eligible requests that is 10 bad events.<Cite id="F3 F4" />
- **Burn rate** = observed bad-event ratio ÷ allowed bad-event ratio. 1% bad ÷ 0.1% allowed = 10x burn.<Cite id="F3 F4" />
- **Percentiles**: sort the durations and take the stated quantile. Sorted 100, 120, 150, 180, 220 ms gives p50 = 150 ms. Interpolation has no universally accepted method, and five points are too few for a stable tail estimate.<Cite id="F5 F6" />
- **TTFT** = timestamp(first generated token) − timestamp(prompt submitted). A prompt sent at 12:00:00.000 whose first generated token is observed at 12:00:00.420 gives 420 ms.<Cite id="F7" />
- **Output tokens per second** = tokens generated during a stated interval ÷ interval duration. If 240 tokens are generated after the first token in 8 seconds, throughput for that interval is 30 tokens/s. Report TTFT alongside it.<Cite id="F7 F8" />
- **Cache read share** = `cache_read_input_tokens` ÷ (`cache_read_input_tokens` + `cache_creation_input_tokens` + `input_tokens`). 8,000 read + 2,000 write + 1,000 uncached gives 8,000 ÷ 11,000 = 72.7% read share, which is not a hit rate.<Cite id="F11" />
- **Request cache hit rate** = requests with `cache_read_input_tokens` greater than zero ÷ cache-eligible requests. 720 read-hit requests ÷ 900 eligible repeats = 80%. Here, exclude first writes and requests that have no reusable prefix.<Cite id="F38" />
- **Effective input cost** = [(uncached × base rate) + (write tokens × base rate × write multiplier) + (read tokens × base rate × read multiplier)] ÷ 1,000,000. At an illustrative $3/MTok, 1,000 uncached tokens, 2,000 five-minute write tokens at 1.25x, and 8,000 read tokens at 0.1x give (3,000 + 7,500 + 2,400) ÷ 1,000,000 = $0.0129. Substitute your model's actual rates and multipliers.<Cite id="F11 F14 F15" />
- **Cost per successful task** = total cost for all attempts ÷ successful tasks. $120 ÷ 800 successful tasks = $0.15 per success, with failed attempts and retries left in the numerator.
- **Retry amplification** = provider attempts ÷ original logical operations. 1,400 ÷ 1,000 = 1.4x, that is 40% extra attempts; separate SDK retries from application retries before you diagnose it.<Cite id="F30" />
- **Pass@k**, with a fixed independent per-attempt success probability p, = 1 − (1 − p)^k. p = 0.8, k = 3 gives 1 − 0.2³ = 99.2% chance that at least one attempt succeeds. Benchmark estimators may differ from this plug-in formula.<Cite id="F33" />
- **Pass^k** = p^k for independent runs; from n trials with c passes on one task, estimate C(c,k) ÷ C(n,k), zero when the pass count is below k, then average that ratio across tasks. p = 0.8, k = 3 gives 0.8³ = 51.2% all-three success.<Cite id="F31 F32" />
- **Precision, recall, F1**: P = TP ÷ (TP+FP), R = TP ÷ (TP+FN), F1 = 2PR ÷ (P+R). TP = 8, FP = 2, FN = 4 gives P = 0.80, R = 0.667, F1 = 0.727.<Cite id="F23 F24 F37" />
- **Recall@k** = relevant items in the top k ÷ all known relevant items for the query. 3 of 5 relevant passages inside the first 10 results gives Recall@10 = 0.60. Choose the unit that enters the context: document, chunk, or evidence span.
- **Cohen's κ** = (Po − Pe) ÷ (1 − Pe). Po = 0.90 and Pe = 0.60 give 0.30 ÷ 0.40 = 0.75. Report prevalence and raw agreement alongside it.<Cite id="F25" />
- **Power and MDE**: power = P(reject H0 given a specified alternative) = 1 − β; MDE is the smallest effect δ for which the planned power(δ; n, variance, α) reaches the target. At α = 0.05 and 80% power, a design calculator might report +5 percentage points as the MDE for its own sample size and baseline variance; that threshold is design-dependent, not universal.<Cite id="F26 F27" />
- **Little's law**: L = λW under steady state. 40 accepted tasks/s with 2 s average in-system time implies 80 tasks in the system on average. Use steady-state averages, one system boundary, and matching time units.<Cite id="F28" />

## API facts to re-check before you rely on them

Final Messages API responses expose `usage.input_tokens` and `usage.output_tokens`; under caching, total input also adds `cache_creation_input_tokens` and `cache_read_input_tokens`, so never use `input_tokens` alone as total prompt input.<Cite id="F11 F12 F19" /> Cache fields appear in response usage, or in `message_start` when streaming; token counts in streaming `message_delta` events are cumulative.<Cite id="F10 F38" />

<Callout type="version" title="Version-sensitive, verified 2026-11-19">
Prompt-cache minimum lengths vary by model — shorter prompts cannot be cached even when marked with `cache_control` — and cache read and write multipliers differ by model and may change, so consult the current prompt-caching and pricing pages before setting thresholds or forecasting spend.<Cite id="F14 F15 F35" /> The documented SDK retry default of two retries with exponential backoff is likewise an SDK-version-dependent behavior.<Cite id="F30" />
</Callout>

Standardize units, windows, and the aggregation method for latency histograms across services: OpenTelemetry histograms exist for statistics such as summaries and percentiles,<Cite id="F22" /> metrics are measurements captured at runtime,<Cite id="F34" /> and percentile interpolation has no universally accepted method.<Cite id="F6" />

## Measurement practice

- **Define task completion before you define the SLI.** HTTP success can still be a refusal, an incomplete answer, a failed tool sequence, or a wrong extraction; keep infrastructure success and task success as separate indicators.
- **Track TTFT and end-to-end tail latency separately.** Streaming can make output visible sooner while tools or generation still miss your completion objective.
- **Use cache read share for cost composition and the request-level hit rate for cache behavior,** and measure only eligible repeats.
- **Specify the experiment metric, baseline, randomization unit, alpha, power, and minimum useful effect in advance.** Account for correlation between user turns when estimating sample size.
- **Match the estimator to the question:** pass@k when you can select among candidates, pass^k for repeated-run consistency. For capacity, pair arrival rate, residence time, and concurrency; persistent queue growth means arrivals exceed completions.

## Where usage connects to outcomes

Record timestamps and token usage on every model call, and count only validated terminal outcomes as successes. Attribute usage from retries and tool loops to the terminal outcome when calculating cost per success.

## Worked example: one day of an extraction service

An extraction service has a 99.9% 30-day SLO and receives 10,000 requests/day. On one day it logs 100 task failures and 1,200 provider attempts for 1,000 logical operations. Usage for that day shows 50,000 cache-read tokens, 10,000 cache-write tokens, and 5,000 uncached tokens. Assume $3/MTok with five-minute write and read multipliers of 1.25x and 0.1x. The arithmetic is hand-runnable.

1. Daily task success ratio = 9,900 ÷ 10,000 = **99%**. One day's measurement does not determine whether a rolling 30-day SLO is met; calculate over the actual objective window.<Cite id="F1 F2" />
2. Objective error ratio = 1 − 0.999 = **0.1%**, so today's 1% failure ratio is **10x burn** relative to the allowed rate.<Cite id="F3 F4" />
3. Retry amplification = 1,200 ÷ 1,000 = **1.2x**. Attribute the extra attempts to SDK retry, application retry, or duplicate submissions before you mitigate.<Cite id="F30" />
4. Cache read share = 50,000 ÷ (50,000 + 10,000 + 5,000) = **76.9%**.<Cite id="F11" />
5. Effective input charge = [(5,000 × 3) + (10,000 × 3 × 1.25) + (50,000 × 3 × 0.1)] ÷ 1,000,000 = (15,000 + 37,500 + 15,000) ÷ 1,000,000 = **$0.0675** at these illustrative prices. Recalculate against the actual model price and applicable multipliers.<Cite id="F14 F15" />

## Common mistakes

- Calling `input_tokens` divided by total input the cache hit rate. `input_tokens` excludes both cache reads and cache writes, so compute the complete total first.<Cite id="F11 F12" />
- Summing streaming usage snapshots when the `message_delta` token counts are already cumulative.<Cite id="F10" />
- Comparing p99 values produced by different interpolation or aggregation methods as if the difference necessarily showed a regression.<Cite id="F6" />
- Dividing output tokens by total request duration to claim generation throughput; that denominator may include TTFT plus queue and tool delay.<Cite id="F7" />
- Reporting pass@k as a guarantee that every repeated production run succeeds; pass^k is the all-success event.<Cite id="F31 F33" />
- Reporting raw rater agreement without prevalence context or chance-adjusted kappa, or treating qualitative kappa cutoffs as universal.<Cite id="F25" />
- Treating the MDE as the observed effect, or reading low power as evidence that no effect exists.<Cite id="F26" />
- Applying Little's law to unstable queues, or mixing a per-second arrival rate with a millisecond residence time without unit conversion.<Cite id="F28" />
- Routing refusals, context overflow, and transient transport errors through one generic retry path; stop reasons and API errors need distinct handling.<Cite id="F17 F30" />

## Exam lens

<ExamLens>
When a scenario defines an SLI, distinguish response success from task success before choosing the numerator. When it shows usage fields, do not read `input_tokens` or a token read share as total input or as a request hit rate. When it reports speed, separate TTFT, completion latency, and tail behavior. When it reports an agent benchmark, choose pass@k versus pass^k for the outcome actually measured, and check whether the study had the power to detect the difference it claims.
</ExamLens>

## Self-check

<SelfCheck question="A request has 500 uncached input tokens, 1,000 cache-write tokens, and 8,500 cache-read tokens. What are total input and read share?">
Total input is 500 + 1,000 + 8,500 = 10,000 tokens and the read share is 8,500 ÷ 10,000 = 85%.<Cite id="F11" />
</SelfCheck>

<SelfCheck question="A system succeeds independently 90% of the time. What are pass@2 and pass^2?">
Pass@2 = 1 − 0.1² = 99%: at least one of two attempts succeeds.<Cite id="F33" /> Pass^2 = 0.9² = 81%: both attempts succeed.<Cite id="F31" />
</SelfCheck>

<SelfCheck question="A 99.9% SLO sees 0.5% bad requests in a window. What is the burn rate, and what does it mean?">
0.005 ÷ 0.001 = 5x: the service is consuming its error budget five times faster than the objective allows.<Cite id="F3 F4" />
</SelfCheck>
